# Dictionary And Ranking Boundary

Cassotis IME for Linux consumes the same SQLite artifacts generated by
[Cassotis Lexicon](https://github.com/shenmin/cassotis-lexicon) as the Windows
v1.20.0 baseline. Base artifacts are read-only. Learning, preferences, and
completion feedback are stored in a separate per-user SQLite database shared
by IBus and Fcitx 5.

## Release Compatibility

- Current source baseline schema: `24`
- Minimum readable schema: `18`
- Frozen baseline simplified database SHA-256:
  `f4357388d78cc7557def22469ee631f766cf872c96e9330f47c7a196fcd192a8`
- Frozen baseline traditional database SHA-256:
  `faa35b6793da5e99e0f135a96b9986836b81568e38296456d999108a8c83bc5b`
- Simplified/traditional base rows: 213,077 / 216,229
- Simplified/traditional completion-competition rows: 42,453 / 42,448
- Simplified/traditional completion pair-audit rows: 4,379 / 4,379
- Simplified long-completion rows: 35,423 visible paths and 97,589 total
  text-recall rows
- Traditional long-completion rows: 32,481 visible paths and 92,457 total
  text-recall rows
- Schema source: `meta(key = 'schema_version')`
- Runtime SQLite access: UTF-8, base database opened read-only

Schemas 18 through 23 remain readable where their optional signal tables are
available, but complete v1.20.0 ranking and completion parity is release-gated
only with the frozen schema-24 artifacts. A newer schema is accepted only
while every table and column used by this engine remains compatible.
Source parity validates both database hashes and the lexical, competition,
pair-audit, and long-completion row counts, so a stale importer cannot silently
turn completion artifacts into unusable base rows or omit required signals.

## Base Signals

The production provider uses all signals consumed by the v1.20.0 engine, not
only a flat pinyin/weight table:

| Area | Main data |
| --- | --- |
| Lexical recall | `dict_base`, pinyin aliases, `dict_jianpin` |
| Segmented paths | query-path priors and word transition weights |
| Language models | forward and reverse character n-gram tables |
| Popularity | text/substring popularity priors |
| One-key completion | exact-prefix lookup, transition, prior, competition, pair-audit, and expanded long-completion recall tables |

Exact, alias, jianpin, indexed prefix, segmented path, and completion queries
remain bounded and index-backed. The provider batches n-gram keys and reuses
query-local caches so the multi-stage ranker does not repeatedly scan the
dictionary.

## Candidate Pipeline

The shared Free Pascal engine owns the complete candidate pipeline:

1. Decode full pinyin or one of six shuangpin schemes to canonical pinyin.
2. Recall exact/user entries, aliases, jianpin, prefixes, stored query paths,
   and lexicon-constrained segmented paths.
3. Keep short exact-input and long-sentence paths separate so sentence search
   cannot displace a valid short exact pool accidentally.
4. Merge all candidate sources and apply fixed single-character rules, user
   evidence, context signals, word/path priors, character models, and the 42
   generated ranking units plus bounded document-local evidence.
5. For an ambiguous long-sentence pool only, jointly score the canonical
   Pinyin and up to 16 bounded final candidates with the conditional
   Transformer. A separate constrained generator may add complete Pinyin-
   aligned candidates that static recall missed; learned invocation and fusion
   gates decide whether generated output may alter the final order. Missing,
   late, or abstaining inference leaves the deterministic order unchanged;
   short exact queries never enter this stage.
6. Return one final ordered list plus a separate one-key completion.

The generated model units and expanded evidence are mechanically compared
against the frozen Windows source by
`tools/parity/validate_source_parity.py`. Corpus-scale behavior is measured by
the native Linux runner documented in [../BENCHMARK.md](../BENCHMARK.md)
([简体中文](../BENCHMARK.CN.md)).

## User Database

The user database records learned exact/literal candidates, aggregate usage,
latest query choices, context-query choices, path preferences/penalties,
bigram/trigram evidence, fuzzy choices, and completion feedback. Writes use
short transactions and WAL; framework contexts observe the same engine-owned
state immediately. Restart-persistence, cross-context visibility, deletion,
and concurrent framework access are covered by service and adapter tests.

Only candidates backed by removable persistent user data carry the deletable
flag. Base, path, generated, and partially composed candidates cannot expose a
delete control.

## One-Key Completion

Completion is computed separately from ordinary candidates and therefore
cannot reorder them. A complete prefix of at least two syllables may use
exact/user continuation, transition evidence, or the controlled long-prefix
path. Feedback is persisted independently from ordinary candidate learning.

When those deterministic tiers have no result for an eligible long prefix,
the engine may enqueue a bounded local-completion request. The v1.20 index
recalls exact-lexicon continuations from multiple word- and character-suffix
levels, then a native selector bounds the pool before the CPU-only path model
compares at most 32 suffix paths. If that pool has no accepted result, a
constrained local generator may propose one suffix under its own confidence
gate. Both paths emit at most three words within six syllables and may abstain.
Results that exceed the time budget or no longer
match the active context generation are discarded.

The configured Tab or backtick key commits the visible completion. A paging
configuration that consumes the same Tab key is rejected.

## Runtime Paths

The engine searches a user data directory first, then the system release data:

```text
~/.local/share/cassotis-ime/dict_sc.db
~/.local/share/cassotis-ime/dict_tc.db
~/.local/share/cassotis-ime/user_dict.db
/usr/share/cassotis-ime/dict_sc.db
/usr/share/cassotis-ime/dict_tc.db
```

`CASSOTIS_DICTIONARY`, `CASSOTIS_TRADITIONAL_DICTIONARY`, and
`CASSOTIS_USER_DICTIONARY` provide explicit paths for tests and staged
installations. User data is never written into a base artifact.

## Inspection And Validation

Inspect a final database without starting an input framework:

```bash
./build/bin/cassotis-engine --dict-query /path/to/dict_sc.db shijie 9
```

Run frozen candidate parity:

```bash
./scripts/validate_candidates.sh --dictionary /path/to/dict_sc.db
```

Run the full native quality benchmark and validate its case counts/invariants:

```bash
./build/bin/cassotis-quality-benchmark \
  --dictionary /path/to/dict_sc.db \
  --long-cases /path/to/long_sentence_16300.tsv \
  --short-cases /path/to/word_input_yhwd_context.tsv \
  --neural-runtime ./build/bin \
  --report-dir ./quality-report

python3 tools/parity/validate_quality_report.py \
  --summary ./quality-report/quality-summary.txt \
  --dictionary /path/to/dict_sc.db \
  --long-cases /path/to/long_sentence_16300.tsv \
  --short-cases /path/to/word_input_yhwd_context.tsv
```
